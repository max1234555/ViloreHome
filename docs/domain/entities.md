# DDD-модель ViloreHome

## Межі роботи

ViloreHome зараз є каталогом товарів: ASP.NET Core API зберігає `Item` у SQLite та надає список через `GET /api/Items`. Контексти замовлень, оплат і складу нижче є цільовою моделлю для розвитку інтернет-магазину, а не вже реалізованими можливостями.

Для практичної моделі обрано модульний моноліт: кожен bounded context має власну предметну модель і відповідає за свої правила. Навчальні класи з `Web-prog_server/Domain/` поки не підключені до API чи Entity Framework Core. Наявний `Models/Item` залишається без змін.

## Піддомени та bounded contexts

| Піддомен | Bounded context | Відповідальність | Статус у проєкті |
|---|---|---|---|
| Каталог | `Catalog` | Товари, категорії, назви та ціни | Частково реалізований через `Item` |
| Користувачі | `Users` | Профіль покупця та його ідентифікація | Запропонований |
| Замовлення | `Orders` | Склад замовлення та його життєвий цикл | Запропонований |
| Оплати | `Payments` | Стан і сума платежу за замовленням | Запропонований; інтеграції з банком немає |
| Склад | `Inventory` | Доступна кількість і резерв товару | Запропонований |

Історія замовлення належить контексту `Orders`: її можна будувати за подіями життєвого циклу замовлення. Рухи залишків належать `Inventory`. Окремий контекст аудиту для цієї навчальної моделі не вводиться.

## Сутності та атрибути

### Users — `User`

- `Id`: унікальний ідентифікатор.
- `Email`: адреса для зв'язку та входу.
- `DisplayName`: ім'я, яке показується в інтерфейсі.
- `CreatedAt`: час створення профілю.
- `IsActive`: чи може користувач оформлювати замовлення.

Правила: email і відображуване ім'я не можуть бути порожніми.

### Catalog — `Product`, `Category`

`Product`:

- `Id`: ідентифікатор товару.
- `Name`: назва.
- `Description`: опис.
- `Price`: поточна ціна у валюті магазину.
- `CategoryId`: ідентифікатор категорії.
- `IsActive`: чи показується товар у каталозі.

`Category`:

- `Id`: ідентифікатор категорії.
- `Name`: назва категорії.

Правила: назва товару й категорії обов'язкова; ціна товару не може бути від'ємною. `OrderItem` зберігає ціну на момент додавання, щоб подальша зміна ціни каталогу не змінювала вже створене замовлення.

### Orders — `Order`, `OrderItem`

`Order`:

- `Id`: ідентифікатор замовлення.
- `CustomerId`: ідентифікатор покупця з контексту `Users`.
- `CreatedAt`: час створення.
- `Status`: `Draft`, `AwaitingPayment`, `Confirmed` або `Cancelled`.
- `Items`: позиції замовлення.
- `Total`: сума позицій, обчислюється з кількості та зафіксованої ціни.

`OrderItem`:

- `ProductId`: ідентифікатор товару з `Catalog`.
- `ProductName`: назва на момент замовлення.
- `UnitPrice`: ціна одиниці на момент замовлення.
- `Quantity`: додатна кількість.

Правила: змінювати позиції можна лише у чернетці; до оплати можна перейти лише з непорожнім замовленням; підтвердження можливе лише після успішної оплати.

### Payments — `Payment`

- `Id`: ідентифікатор платежу.
- `OrderId`: ідентифікатор замовлення.
- `Amount`: сума платежу.
- `Status`: `Pending`, `Succeeded`, `Failed` або `Refunded`.
- `CreatedAt`: час створення платежу.

Правила: сума має бути більшою за нуль; завершений платіж не можна повторно позначити успішним; повернення дозволене лише для успішного платежу. Реальна платіжна система до прототипу не входить.

### Inventory — `InventoryItem`

- `ProductId`: ідентифікатор товару з `Catalog`.
- `OnHand`: фізична кількість на складі.
- `Reserved`: зарезервована кількість.
- `Available`: доступна кількість (`OnHand - Reserved`).

Правила: кількості не від'ємні; резервування не може перевищувати доступний залишок; після відвантаження резерв зменшується разом із фізичним залишком.

## Прототип коду

Навчальні реалізації сутностей та базових бізнес-операцій містяться у `Web-prog_server/Domain/`, розділені за bounded contexts. Вони демонструють інваріанти, але поки не мають EF-конфігурацій, сховищ чи API endpoint-ів.
