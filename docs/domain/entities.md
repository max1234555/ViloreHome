# DDD-модель ViloreHome

## Межі роботи

ViloreHome наразі надає API каталогу товарів: ASP.NET Core зберігає `Item` у SQLite та повертає список через `GET /api/Items`. Моделі в `Web-prog_server/Domain/` — навчальний прототип домену магазину. Вони не підключені до API чи Entity Framework Core і самі по собі не створюють реальних процесів замовлення, оплати або обліку складу.

У коді виділено модулі `Users`, `Catalog`, `Orders`, `Payments` та `Inventory`. Нижче поля, початкові стани й правила описані відповідно до реалізованих класів, а не до майбутніх можливостей.

## Піддомени та bounded contexts

| Піддомен | Bounded context | Відповідальність | Реалізація |
|---|---|---|---|
| Користувачі | `Users` | Ім'я та email користувача | `User` у доменному прототипі |
| Каталог | `Catalog` | Товари, ціни та категорії | `Product` і `Category` у доменному прототипі; чинний API окремо використовує `Models/Item` |
| Замовлення | `Orders` | Позиції та статуси замовлення | `Order`, `OrderItem`, `OrderStatus` у доменному прототипі |
| Оплати | `Payments` | Сума, валюта та статус платежу | `Payment`, `PaymentStatus` у доменному прототипі; платіжного провайдера немає |
| Склад | `Inventory` | Фізична кількість, резервування та відвантаження | `InventoryItem` у доменному прототипі |

## Сутності та правила

### Users — `User`

Поля:

- `Id`: згенерований GUID користувача.
- `Name`: ім'я; під час створення та перейменування не може бути порожнім, обрізається по краях.
- `Email`: email; під час створення та зміни не може бути порожнім, обрізається по краях.

Методи: `Rename(name)` змінює ім'я; `ChangeEmail(email)` змінює email.

### Catalog — `Product`, `Category`

`Product`:

- `Id`: згенерований GUID товару.
- `CategoryId`: GUID категорії; не може бути порожнім.
- `Name`: назва; не може бути порожньою.
- `Description`: необов'язковий опис.
- `Price`: ціна; має бути більшою за нуль.

Методи: `Rename(name)` змінює назву; `ChangePrice(price)` встановлює додатну ціну.

`Category`:

- `Id`: згенерований GUID категорії.
- `Name`: назва; не може бути порожньою.
- `Description`: необов'язковий опис.

Метод: `Rename(name)` змінює назву категорії.

### Orders — `Order`, `OrderItem`, `OrderStatus`

`Order`:

- `Id`: згенерований GUID замовлення.
- `UserId`: GUID власника замовлення; не може бути порожнім.
- `CreatedAt`: час створення в UTC.
- `Status`: початково `Pending`.
- `Items`: позиції замовлення.
- `Total`: обчислювана сума `LineTotal` усіх позицій.

`OrderItem`:

- `ProductId`: GUID товару; не може бути порожнім.
- `ProductName`: назва товару; не може бути порожньою.
- `UnitPrice`: ціна одиниці на момент додавання; має бути більшою за нуль.
- `Quantity`: кількість; має бути більшою за нуль.
- `LineTotal`: обчислювана сума `UnitPrice * Quantity`.

Метод `ChangeQuantity(quantity)` змінює кількість на додатну. `Order.AddItem(...)` додає нову позицію з переданими даними; однакові товари окремо не об'єднуються. У поточному коді `ChangeQuantity` не перевіряє статус батьківського замовлення, тому кількість позиції можна змінити і після підтвердження; відповідно, обчислюваний `Total` також зміниться. Це обмеження реалізації.

Статуси й переходи замовлення:

| Поточний статус | Операція | Новий статус / умова |
|---|---|---|
| `Pending` | `AddItem(...)` | Додає позицію |
| `Pending` | `Confirm()` | `Confirmed`, лише якщо замовлення непорожнє |
| `Confirmed` | `MarkPaid()` | `Paid` |
| `Paid` | `Ship()` | `Shipped` |
| `Shipped` | `Complete()` | `Completed` |
| `Pending` або `Confirmed` | `Cancel()` | `Cancelled` |

Інші переходи статусу заборонені. Додавати позиції можна лише у статусі `Pending`. Метод `OrderItem.ChangeQuantity` є окремим публічним методом і не має такої перевірки статусу.

### Payments — `Payment`, `PaymentStatus`

Поля:

- `Id`: згенерований GUID платежу.
- `OrderId`: GUID замовлення; не може бути порожнім.
- `Amount`: сума; має бути більшою за нуль.
- `Currency`: валюта; не може бути порожньою, зберігається великими літерами.
- `Status`: початково `Pending`.

У моделі немає поля часу створення платежу. Методи `MarkSucceeded()` і `MarkFailed()` переводять платіж лише з `Pending`; `Refund()` дозволений лише зі статусу `Succeeded`. Інтеграції з платіжною системою немає.

### Inventory — `InventoryItem`

Поля:

- `ProductId`: GUID товару; не може бути порожнім.
- `QuantityOnHand`: фізична кількість; початкове значення не може бути від'ємним.
- `ReservedQuantity`: зарезервована кількість.
- `AvailableQuantity`: обчислюється як `QuantityOnHand - ReservedQuantity`.

Методи:

- `Reserve(quantity)`: резервує додатну кількість, якщо її не більше за доступну.
- `ReleaseReservation(quantity)`: знімає додатну кількість, не більшу за резерв.
- `FulfillReservation(quantity)`: зменшує резерв і фізичний залишок на додатну кількість, не більшу за резерв.
- `AddStock(quantity)`: додає додатну кількість до фізичного залишку.

## Важливі обмеження прототипу

Моделі описують локальні правила кожного класу. Узгодження оплати із замовленням, атомарність операцій між контекстами, збереження в базі, API та зовнішні інтеграції тут не реалізовані.
