# ADR 0003: REST API та модель помилок

- **Статус:** прийнято
- **Дата:** 2026-11-15
- **Область:** реалізований API ресурсу `Items`

## Контекст

Для API каталогу потрібно узгодити маршрути, DTO, HTTP-статуси й формат бізнес-помилок із фактичною реалізацією та контрактом OpenAPI.

## Рішення: REST

Використовуємо ресурс `/api/items` із цілочисельним ідентифікатором:

| Метод | Шлях | Успішний статус | Призначення |
|---|---|---|---|
| `GET` | `/api/items` | `200 OK` | Отримати список товарів |
| `GET` | `/api/items/{id}` | `200 OK` | Отримати товар за ID |
| `POST` | `/api/items` | `201 Created` | Створити товар; відповідь містить `Location` |
| `PUT` | `/api/items/{id}` | `200 OK` | Повністю оновити назву, категорію та ціну |
| `DELETE` | `/api/items/{id}` | `204 No Content` | Видалити товар без тіла відповіді |
| `GET` | `/health` | `200 OK` | Перевірити доступність; тіло — `ok` |

`PATCH` не реалізований. `POST` приймає `CreateItemRequest`, `PUT` — `UpdateItemRequest`, успішні відповіді з товаром використовують `ItemResponse`.

## Валідація та бізнес-помилки

Сервіс вимагає непорожні `name` і `category`, а також `price > 0`. Пробіли по краях назви й категорії обрізаються.

Бізнес-помилки сервісу мають спільну структуру:

```json
{
  "error": "ValidationError",
  "code": "ITEM_VALIDATION_FAILED",
  "details": [
    { "field": "Name", "message": "Name is required." }
  ]
}
```

- `400 Bad Request` — сервіс відхилив дані (`ITEM_VALIDATION_FAILED`).
- `404 Not Found` — товар із таким ID відсутній (`ITEM_NOT_FOUND`).
- `error` описує тип помилки, `code` є машинним кодом, `details` містить пояснення для полів.

`ErrorResponse` описує помилки, сформовані сервісом. `[ApiController]` може автоматично повертати `400 ValidationProblemDetails` для помилок прив'язки запиту або некоректного JSON. Повна уніфікація таких framework-помилок у поточному коді не налаштована.

## Відповідність OpenAPI

Контракт у [`docs/api/openapi.yaml`](../api/openapi.yaml) описує наявні маршрути, DTO, статуси та формат бізнес-помилок. Зміни API потрібно супроводжувати оновленням контракту та перевіряти його у [Swagger Editor](https://editor.swagger.io/).

## Наслідки

REST-маршрути та DTO роблять API передбачуваним для клієнтів. OpenAPI слугує спільним описом контракту. Потрібно підтримувати його відповідність коду; у разі вимоги єдиного формату для всіх помилок необхідно окремо налаштувати обробку автоматичних помилок ASP.NET Core.
