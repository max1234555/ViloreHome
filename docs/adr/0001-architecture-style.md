# ADR 0001: Архітектурний стиль ViloreHome

- **Статус:** прийнято
- **Дата:** 2026-11-15
- **Рішення:** модульний моноліт на поточному етапі

## Контекст

ViloreHome — навчальний командний проєкт каталогу товарів для дому. Наразі працює один ASP.NET Core API з CRUD для `Item`, Entity Framework Core та SQLite. У проєкті є доменні моделі для користувачів, каталогу, замовлень, платежів та інвентарю, але вони поки не підключені до цього API.

Поточний масштаб не потребує незалежного розгортання окремих сервісів або розподіленої інфраструктури.

## Рішення

Розвивати застосунок як **модульний моноліт**: один бекенд, який збирається та запускається як єдине ціле, із логічним розділенням відповідальностей і майбутніх бізнес-модулів. Не створювати мікросервіси й не змінювати схему бази даних лише заради архітектурного стилю.

## Розглянуті альтернативи

| Варіант | Переваги | Недоліки на цьому етапі |
|---|---|---|
| Модульний моноліт (обрано) | Просте локальне розгортання, тестування та налагодження; спільна транзакційна модель | Частини застосунку мають спільний цикл релізу; необхідно зберігати межі модулів |
| Мікросервіси | Незалежні релізи та масштабування окремих сервісів | Мережеві контракти, часткові відмови, додаткова інфраструктура та складніше тестування без потреби для поточного обсягу |

## Наслідки

- Один процес і простіший цикл запуску, тестування та релізу.
- Функціональність каталогу можна розвивати без передчасного розподілення системи.
- Зміни окремих модулів можуть вимагати спільного релізу.
- Потрібно стежити за межами модулів, щоб не змішувати відповідальності.

## Коли переглянути рішення

Повернутися до вибору, якщо з'являться виміряні потреби в незалежному масштабуванні чи розгортанні, окремому володінні даними або якщо спільні релізи почнуть істотно заважати команді.
